# 设备与通信：KI-SX100 / ECHONET Lite

**结论：走局域网 ECHONET Lite，不走 COCORO AIR 云。** 2026-11-02 实测，家里这台 KI-SX100 直接响应局域网 ECHONET Lite，无需账号、token、抓包。切模式和开关加湿都写入成功，并回读确认。

原始记录见 [evidence/kisx100-enl-2026-11-02.txt](evidence/kisx100-enl-2026-11-02.txt)，可用 [evidence/enl_get.py](evidence/enl_get.py) 复测（只发 Get）。

**开关机还没有在真机上操作过**，见 [§6](#6-待验证)。

## 4. Sharp 私有 EPC

这些字节布局没有官方文档。F1、F3 的长度（40、27 字节）和云 API 的同名属性一致，说明云端只是转发 ECHONET 属性。

**可信度**：
- ✅＝这台 KI-SX100 上写入或变化后读回验证过，或和 COCORO AIR 对上
- A＝多个独立项目一致，且实测值合理
- B＝单一来源，或实测值存疑

还没有和机身面板逐一核对。Home Assistant 的 `sharp.py` 只把 FP-S42Y、FX-S120V 列为逐字节验证过的机型，KI-SX100 不在其中。

### F3：运行设置（27 字节，可写）

实测：`00000000 10 0000…00 ff 00 ff 00…`

| 字节 | 含义 | 实测 | 可信度 |
|---|---|---|---|
| 0–3 | 写入掩码；Get 时为 0，主动通知里不为 0 | `00000000` | ✅ |
| 4 | 模式，见下表 | `10`（自动） | ✅ |
| 13 | 电源：`FF` 开 | `FF` | B |
| 15 | 加湿：`FF` 开 | `FF` | ✅ |

| 模式码 | 含义 | 模式码 | 含义 |
|---|---|---|---|
| `10` | 自动 | `14` | 静音 |
| `11` | 夜间 | `15` | 中 |
| `13` | 花粉 | `16` | 强 |
| `30` | 飞沫粒子 | `40` | 效果实感 |
| `20` | AI 自动（其他机型） | | |

这台机器上实测过 `10` 和 `14`：切到 `14` 后功率读到 9 W，和官方“静音 + 加湿 9.0 W”一致，`A0` 也变成 `31`。2026-11-03 在 COCORO AIR 里切模式并只读观察：効果実感是 `40`（12 W，`F2[24]` 从 `81` 变成 `80`，即加湿开着但没在工作），飛沫粒子是 `30`（31 W）。F3[4] 和 F2[27] 同步变化。这两个模式还没从本应用写入过。FP-S42Y 上 `20` 才是“自动”，所以不能跨机型照搬。

实测：`6400c5 19 31 09…`

| 字节 | 含义 | 实测解码 | 可信度 |
|---|---|---|---|
| 3 | 温度（°C，有符号） | 25 | ✅ 和 COCORO AIR 数值相同（读取时间相差约 50 分钟） |
| 4 | 湿度（%） | 49 | ✅ 同上 |
| 12 | 疑似瞬时功率（与 `84` 同为 13） | 13 | B |
| 13–14 | 分钟计数，每分钟 +1；从什么时候算起未知 | 8,164 | B |
| 15–16、17–18 | 离子发生单元累计小时，取较大的。两者目前相等 | 14,317 | ✅ 见“耗材” |
| 19–20 | 常量 720。手册的お手入れ灯约 720 小时亮，可能是这个阈值 | 720 | B |
| 21–24 | **累计净化空气量（m³）**，见下 | 1,722,030 | B |
| 27–28 | PM2.5；`bit15` 无效标记，低 10 位是值。实测在 0 和 1 之间变化 | 0 | B |
| 29–30 | 集尘滤网用量（不是灰尘传感器） | 83 | ✅ 见“耗材” |
| 31–32 | 脱臭滤网用量（不是气味传感器） | 83 | ✅ 见“耗材” |

之前按其他项目把 29–32 叫灰尘、气味，把 37 叫亮度，这在 KI-SX100 上不成立。灰尘、气味的实时读数目前没有找到。

**21–24 为什么是净化空气量**：3.48 分钟涨 12（约 206/小时），约 6.1 小时涨 1,186（约 194/小时）。COCORO AIR 的“きれいにした空気量”同时段是每小时约 190 m³，规格的风量是静音 2.0、中 6.4 m³/分，当时的约 3.4 m³/分落在中间。其他项目把它叫“滤网使用量”或“小时”，按这个速率都不对。

### F0：耗材上限（32 字节，只读）

| 字节 | 含义 | 实测 |
|---|---|---|
| 12–13 | 集尘滤网上限 | 3,000 |
| 14–15 | 脱臭滤网上限 | 3,000 |
| 16–17 | 加湿滤网上限 | 1,250 |
| 18 | Ag+ 离子盒上限（1 字节） | 225 |
| 19–20 | 离子发生单元上限（小时）。手册写约 19,000 小时停止发生离子 | 19,000 |

**耗材**：剩余百分比 = `(上限 − 用量) × 100 / 上限`，向下取整。字段位置来自 [waszkowski/homeassistant-sharp-cocoro-air](https://github.com/waszkowski/homeassistant-sharp-cocoro-air)，它的测试机型是 KI-TX75EU。2026-11-03 在这台 KI-SX100 上和 COCORO AIR 对照，5 项全部一致：

| 耗材 | 用量 / 上限 | 计算 | COCORO AIR |
|---|---|---|---|
| 集尘滤网 | 83 / 3,000 | 97% | 97% |
| 脱臭滤网 | 83 / 3,000 | 97% | 97% |
| 加湿滤网 | 86 / 1,250 | 93% | 93% |
| Ag+ 离子盒 | 86 / 225 | 61% | 61% |
| 离子发生单元 | 14,317 / 19,000 | 24% | 24% |

只比对过这一个时刻。更换耗材后计数器怎么变，还没见过。

### F2：运行状态（40 字节，只读）

实测：`0020…01 ff ff 0000 01 81 ff 00 10 01 …`。采样 3.5 分钟没有变化。

| 字节 | 含义 | 实测 | 可信度 |
|---|---|---|---|
| 19 | 水箱：`FF` 正常 / `00` 低 | `FF` | B |
| 20 | 房间亮灯：`FF` 亮 / `00` 暗 | `FF` | B |
| 23 | 滤网状态：`00` 正常 / `01` 待清洁 | `01` | B（COCORO AIR 此时确实在提示清洁） |
| 24 | 加湿：`00` 关，`81` 加湿中，`82` 缺水；`bit7` 启用，`bit0` 工作中 | `81` | ✅（`00`、`81`）；`82` 未见 |
| 25 | 等离子（来自 FP-S42Y） | `FF` | B |

字节 23 读到 `01` 时，COCORO AIR 正提示加湿滤网、离子单元、集尘盒要清洁，方向一致，但还不知道它对应哪一项，也没见过它清除。应用只在设置页显示一行“设备提示该清洁了”，不发通知。清洁后再读一次才能确认。

## 5. 写入命令

F3 写入时要新建 27 字节命令，只填掩码和目标字段，不要回放读到的值。

| 操作 | 命令（27 字节，其余补 0） | 状态 |
|---|---|---|
| 切模式 | `01 01 00 00 <模式码>` | ✅ 真机（`10`、`14`），不影响加湿 |
| 开加湿 | `00 09 00… [15]=FF` | ✅ 真机，不影响模式 |
| 关加湿 | `00 09 00…`（其余全 0） | ✅ 真机 |
| 开关机 | 标准 `80`：`30` / `31` | ⏳ 未在真机操作 |
| 开关机（备用） | `00 03 00… [13]=FF` 或全 0 | ⏳ 来自云 API；`80` 不生效时才用 |

设备回 `0x71` 只说明接受了命令，每次写入都要回读确认。

风量用 F3 的 `14/15/16`，不用 `A0`：`A0` 的档位在不同项目里映射不一致（高档有 `37` 和 `38` 两种），设备规格也只有三档。

## 7. 协议约束（直接影响实现）

- **必须绑定本机 UDP 3610。** 设备只回复到 3610，临时端口收不到（实测）。
- **一台电脑只跑一个 ECHONET 控制程序。** Go 用多播地址调用 `net.ListenUDP` 时会绑定通配地址，并设置复用选项（macOS 用 `SO_REUSEADDR`+`SO_REUSEPORT`，Windows 用 `SO_REUSEADDR`）。这只保证能绑定成功：发到 3610 的单播回复只会落到其中一个 socket，哪个程序收到没有保证。检测到响应异常时要提示可能有其他 ECHONET 程序。
- **没有可靠传输。** UDP 可能丢包，需要超时重试，用 TID 匹配响应。
- **主动通知只能当信号用。** 一条通知里带多个属性（ESV `0x73`），F3 带掩码；切模式那两次 4 秒内没收到，还有几秒延迟。收到后重新读，平时仍要轮询。
- **设备性能有限。** 请求串行发送，HA 也按设备加了信号量。
- **没有认证。** 同一局域网内任何设备都能控制它，这是协议本身的限制。
- **IP 会变。** 用节点 `83`（EUI-64）识别设备，启动时和连续超时后重新多播发现。部分路由器或 AP 会过滤多播，要提供手动填 IP 的入口。
- **多网卡。** Windows 的 Hyper-V/WSL、VPN 网卡很常见，多播要逐个可用网卡发送。

## 8. 为什么不用云

| | ECHONET Lite（选用） | COCORO AIR 云 |
|---|---|---|
| 账号 | 不需要 | 需要 |
| 凭据 | 无 | 日本区要抓包取 `appSecret`、`terminalAppId` |
| 分发 | 没有障碍 | 不能把 App 的密钥打包发布 |
| 延迟 | 百毫秒内 | 经公网 |
| 离线 | 可用 | 不可用 |
| 稳定性风险 | 私有字节可能随固件变 | 接口和鉴权可能随时变 |
| 远程控制 | 靠 Apple 家庭中枢 | 自带 |

### Go 库

`internal/echonet` 是自己写的。帧格式很简单：`EHD(1081) TID SEOJ DEOJ ESV OPC [EPC PDC EDT]…`，再加发现、重试和 TID 匹配，代码量不大。[uecho-go](https://github.com/cybergarage/uecho-go) 的依赖包含 tview、cobra、viper，对这个桌面应用来说太重。
